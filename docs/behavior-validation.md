# 遊戲行為驗證與重新轉換進度

2026-10-04。使用原始世界重新轉換；世界名稱保持不變。本機未持有 VPS 的原始 MCA 地圖，因此尚未完成兩張完整地圖的重新轉換、客戶端檢查或部署。

## 轉換流程的修改

`CompactTarget.validateSemantics()` 在快取映射結果之前檢查樹葉永久保留／更新旗標、四種冰的種類，以及存在於前後狀態中的珊瑚存活、樓梯上下、半磚位置、門上下與開關、原木軸向、液體深度。發現這些狀態改變會停止，不把它們替換成「看起來不會消失」的其他方塊。

不同版本若改變屬性名稱或表示方法，仍需另寫明確對應並測試；這項檢查不是全面遊戲行為驗證。它不能修正核心對正確狀態的錯誤判讀。

`BatchLoadCheck` 也增加載入後的樹葉判讀檢查；即使方塊狀態讀回相同，只要核心把保留／更新旗標判錯，會以 `CORE_LEAF_SEMANTICS` 停止，不能產生新的載入通過結論。這項新檢查尚未對 VPS 的完整地圖重跑。

不對所有方塊觸發更新，避免連帶腐爛、融化、掉落與啟動紅石。不在來源 MCA 上寫入，也不在伺服器開啟世界時修改 LevelDB。

## 可重現測試

```text
python scripts/test-behavior.py --core /path/to/Nukkit-PM1E-4511.jar --jdk /path/to/jdk
```

會建立新的 `.build-tools/behavior-*` 目錄與僅監聽 localhost 的測試世界。需要取得核心啟動資料的網路連線。結果寫入 `result.json`；原版出現葉片問題會回傳 2。`--leaf-class-dir` 只用於隔離候選的測試類別，不是部署指令。

## 原始地圖的連接樣本

在 VPS 現有已驗證的工作目錄執行：

```sh
python3 scripts/find-connection-sample.py --work /ser/world-converter
```

使用原始核心與既有 `CompactExport.class`，逐個原始區域尋找同材質、水平緊鄰的玻璃片或柵欄。只保留第一個符合的區域、來源中繼資料與座標；不需要玩家提供座標、不改動任何世界。結果位於 `reports/connection-sample-*`。此工具不把不同材質或單獨方塊誤判成應該連接的樣本。

取得樣本後，仍需對照目標狀態及客戶端傳送 palette，才能判定修復位置。兩張完整地圖要在新的乾淨工作目錄重新轉換，不能沿用舊的 completed 標記跳過區域；通過新的載入與客戶端驗證後才替換正式地圖。

## 版本標示與斷線

目前原始碼的 `ProtocolInfo.CURRENT_PROTOCOL=2193`，對外回報字串仍是 `1.26.50`。使用者提供的 1.26.52 畫面也顯示協定 2193；官方對玩家的更新名稱是 [26.52](https://feedback.minecraft.net/hc/en-us/articles/49175370527501-Minecraft-Bedrock-Edition-26-52-Hotfix-Changelog)，而 [Mojang 技術文件](https://github.com/Mojang/bedrock-protocol-docs/releases)仍使用 1.26.x 格式。

RakNet 查詢回應的版本字串由 `RakNetInterface.setName()` 加入，並非只改 MOTD 就能更新。版本字串落差不等於已確認的協定錯誤。尚未完整驗證客戶端進入世界與方塊傳送，不修改正式核心的支援版本宣告，也不將版本標示更動混進樹葉修正 PR。
